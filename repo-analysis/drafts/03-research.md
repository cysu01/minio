# MinIO 調研筆記

## 專案解決的核心問題

**場景 1 - 雲原生私有儲存**：企業需要 S3 相容的物件儲存，但不願依賴 AWS。傳統方案 Ceph 運維複雜度極高（CRUSH map、PG management、多服務協調），MinIO 用單二進位制解決了這個問題。

**場景 2 - AI/ML 資料湖**：PyTorch/TensorFlow 訓練需要從高吞吐儲存中讀取 TB 級資料集。MinIO 專為這類大物件流式讀寫最佳化，官方宣稱 PUT 吞吐可達 325 GiB/s，GET 達 400 GiB/s（NVMe 叢集）。

**場景 3 - 邊緣/混合雲**：單節點部署到多 region 站點複製，同一套 API，無縫擴充套件。

## 競品定位對比

| 專案 | 定位 | 優勢 | 劣勢 |
|------|------|------|------|
| MinIO | 高效能 S3 專用 | 效能最優、S3 相容性最好（382測試透過）、運維簡單 | 僅物件儲存、AGPL 許可證 |
| Ceph RGW | 統一儲存（塊+檔案+物件）| 生態成熟、企業級特性 | 運維極複雜、效能低於 MinIO |
| SeaweedFS | 小檔案高效儲存 | 小檔案 IO 優秀、主從架構簡單 | S3 相容性差（僅56測試透過）|
| Garage | 邊緣輕量儲存 | 極小記憶體佔用、地理分佈 | 功能不完整 |
| RustFS | Rust 重寫的 MinIO 替代 | 記憶體安全、效能潛力 | 尚不成熟 |

## 獨特價值主張

1. **專一性**：只做物件儲存，不做塊儲存和檔案儲存，因此在物件儲存這一維度上效能碾壓 Ceph
2. **運維極簡**：單二進位制部署，無外部依賴，所有節點對等（無 Master 節點），啟動後自動協商
3. **S3 原生**：不是"相容"S3，而是重新實現了 S3 協議的每一個細節，包括 multipart、select、object lock
4. **糾刪碼物件級**：與其他系統的卷級 EC 不同，MinIO 在物件級別做 EC，允許每個物件獨立設定儲存類別

## 重要背景

- 2026年2月，MinIO 社群版 GitHub 倉庫已歸檔（只讀），商業版更名為 AIStor

- 許可證：AGPL v3（任何修改都必須開源）
